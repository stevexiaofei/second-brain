# Inbox Organizer

用于整理个人 second brain 的 `docs/inbox/`。核心流程是：

**扫描 → 理解 → 搜索重复 → 分类 → 提出方案 → 获得确认 → 增量实施 → 验证。**

不要把 Inbox 当成“待格式化的文件夹”，而要把它当成尚未完成理解的临时空间。整理的目标不是清空 Inbox，而是让每条信息进入合适的生命周期阶段，同时保留有价值的上下文。

## Phase 0：建立边界

1. 先阅读 `CLAUDE.md`、`AGENTS.md`，确认仓库的 Markdown、索引、导航和 Git 规则。
2. 检查 Git 状态，把既有未提交改动视为受保护内容；不要重置、覆盖或悄悄合并无关改动。
3. 确认 Markdown 是知识源头，不能用生成的 HTML 代替源文件。
4. 默认只处理 `docs/inbox/` 和整理所必需的索引、导航及相关链接文件。
5. 默认先给出整理报告和实施计划；在用户确认前，不移动、删除、重写或批量改名。

## Phase 1：扫描 Inbox

先搜索，再深入阅读。建立每篇 Inbox 笔记的清单：

- 文件路径、标题、frontmatter、创建/更新时间；
- 内容类型：概念、论文、源码阅读、工程经验、项目、想法、阅读线索或资源地图；
- 当前成熟度：临时记录、待验证、部分理解、可沉淀；
- 已有来源、证据、个人理解和开放问题；
- 可能的目标领域和目标文件；
- 是否与 `docs/knowledge/`、`docs/projects/`、`docs/reading/`、`docs/ideas/` 中的内容重复或互补；
- 是否存在真实但未连接的相关笔记。

如果 Inbox 只有少量笔记，也要确认目录索引和 VitePress 入口是否与实际文件一致。

## Phase 2：分类决策

为每篇笔记选择一个主要处理结果，必要时附带次要动作：

| 结果 | 判断标准 | 典型动作 |
| --- | --- | --- |
| 留在 Inbox | 仍是线索、收藏、问题清单、未验证材料或尚未形成个人理解 | 保留原文，补充状态、下一步或来源 |
| 迁入 Knowledge | 已理解为可复用概念、论文、源码阅读或工程经验 | 移动到正确主题目录，保留内容并补索引、sidebar、链接 |
| 迁入 Projects | 具有明确目标、状态、决策和下一步的进行中事项 | 移动到 `docs/projects/`，补项目入口和状态结构 |
| 迁入 Reading | 主要是书籍、论文或外部材料的阅读记录，且不应成为稳定知识 | 移动到 `docs/reading/` 或对应阅读索引 |
| 迁入 Ideas | 主要是未来想法、假设或待验证方向，不是当前知识 | 移动到 `docs/ideas/` 或对应索引 |
| 合并/扩展已有笔记 | 内容与现有笔记高度重叠，新增独立文件会造成重复 | 先指出目标笔记和保留内容，再经确认合并；不得静默覆盖 |
| 拆分 | 一个文件混合多个相对独立且已有充分内容的概念 | 仅在用户明确批准后拆分；否则记录为延期 |

### 分类原则

- 先按**主题**找目标目录，再按文档类型选择文件形态。
- 一篇笔记只选一个 canonical 归属；交叉领域通过链接表达，不复制文件。
- 没有足够理解时不要强行迁入 Knowledge；“留在 Inbox”是有效结果。
- 不为了补齐分类而创建空的占位笔记或虚构个人经验。
- 对论文保留问题、方法、实验、局限、个人理解和开放问题。
- 对工程/调试经验保留环境、症状、调查、根因、解决方案和经验教训。
- 明确区分外部事实、个人理解、实际经验、推测和未解决问题。

## Phase 3：搜索重复与建立连接

对每篇候选迁移笔记：

1. 搜索标题、核心术语、来源和关键结论，查找已有概念或近似笔记。
2. 区分“重复”“互补”“上下游前置知识”和“仅仅共享关键词”。
3. 如果已有 canonical 笔记，优先更新或链接已有笔记，不要创建第二份事实来源。
4. 检查迁移后的相对链接、主题索引、父目录索引和 VitePress sidebar。
5. 只使用实际存在的 Markdown 链接；外部资料可以使用真实 URL。

## Phase 4：输出整理计划并确认

在修改前，用中文报告：

### 整理总览

- Inbox 当前文件数和状态；
- 已确认可迁移、建议保留、疑似重复、需要用户判断的数量；
- 不会处理的范围。

### 逐文件决策表

| 当前文件 | 判断 | 目标 | 动作 | 依据 | 风险/待确认 |
| --- | --- | --- | --- | --- | --- |

### 实施边界

明确列出：

- 将移动、更新、合并或新增的精确文件；
- 将更新的 Inbox、Knowledge、Projects、Reading、Ideas 索引；
- 将更新的 VitePress sidebar 和跨笔记链接；
- 明确延期、不确定或需要用户亲自补充的事项；
- 验证命令和预期结果。

除非用户已经给出完整且明确的实施指令，否则等待用户确认后再修改。

## Phase 5：安全实施

确认后：

1. 使用版本控制感知的移动方式，保持 Git 历史和内容完整。
2. 先移动/更新内容，再同步索引和导航，避免出现孤立页面。
3. 移入或移出 `docs/inbox/` 时同步更新 `docs/inbox/index.md` 的 Notes 区域。
4. 移入 `docs/knowledge/` 时同步更新目标父目录 `index.md` 和 `docs/.vitepress/config.mts`；其他 VitePress 内容目录也遵循相应索引规则。
5. 修复移动导致的相对路径、旧路径和跨领域链接。
6. 合并时保留原始上下文、来源和个人理解；不要静默删除信息。
7. 只在笔记有实质内容变化时更新 `updated`。
8. 不修改与本次 Inbox 整理无关的文件，不提交或推送，除非用户明确要求。

## Phase 6：验证与交付

尽可能运行：

- Inbox Notes 索引与实际文件一致性检查；
- 目标目录索引和 VitePress sidebar 目标检查；
- Markdown 相对链接扫描，并区分代码示例误报；
- 搜索旧路径、孤立入口和本地 `file:///` 链接；
- `git diff --check`；
- 仓库的文档构建或测试。

交付时如实说明：

- 每篇 Inbox 笔记的最终去向；
- 创建、更新、移动、合并和延期的文件；
- 索引、sidebar 和链接修复；
- 通过、失败、未执行及被环境阻断的验证；
- 仍需用户理解、补充或决定的内容。

绝不把“文件被移动”描述成“知识已经被理解”。
