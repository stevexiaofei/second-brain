# Interactive Explainer Animation

当用户希望在知识笔记、教程或技术文档中加入交互动画，用来理解复杂算法、系统状态、数据流、时序或组件协作时使用。目标是让读者能**观察并操作机制**，不是为了装饰页面而增加运动效果。

适用于：

- 有多个阶段、状态转换或并发关系的算法 / 系统行为；
- 数据在 rank、设备、队列、bucket、节点或张量分片之间的流动；
- 静态图难以表达的先后顺序、等待、重试、聚合、拆分或变化；
- 用户明确要求“动画”“交互式演示”或帮助理解一段复杂内容。

不适用于：简单概念、单一结构关系或静态图已经足够清晰的内容。若动画不能让读者回答一个具体问题，应优先改进说明、示例或静态图。

## 工作原则

1. **准确性先于动效**：每个画面状态都必须对应真实机制；动画只是解释模型，不能制造实现中不存在的语义。
2. **围绕一个学习目标**：先说清读者看完应能解释什么，再决定表现形式和交互。
3. **最小但完整的例子**：选择读者能跟踪的最小 rank 数、参数数、状态数或数据块数；覆盖关键路径和容易误解的边界。
4. **说明简化假设**：显式标出哪些被省略（例如真实桶大小、通信耗时、拓扑、并发细节或数值）；不得把示意模型写成完整实现。
5. **复用现有模式、保护工作树**：先搜索已有组件与用户改动，优先小改和复用；不覆盖、重排或顺手清理无关修改。
6. **先验证再交付**：核对机制、组件构建、实际交互和布局；无法做的检查必须明确说明，不得把 SSR 或静态输出称为浏览器交互验证。

## Phase 0：建立上下文和边界

1. 阅读仓库的 `CLAUDE.md` / `AGENTS.md` 及相关项目规范；确认知识源文件、构建方式和导航规则。
2. 查看 `git status`。将所有既有未提交改动视为受保护内容；不 reset、不覆盖、不混入无关改动。
3. 搜索目标文档、同主题页面、现有图表 / 交互组件和组件注册方式。先扩展已有演示，只有不能复用时才新建。
4. 找到目标机制的 source of truth：源码、公式、论文或已有经过核验的说明。对不确定的行为先研究，不从图形直觉补写事实。
5. 明确交付范围：目标 Markdown、组件、主题注册、必要的索引 / 导航和验证项。VitePress 目录不能自动扫描时，按项目规则更新入口。

## Phase 1：提炼学习目标与动画模型

实现前写下以下内容（可作为内部设计清单，复杂或多文件改动时先给用户实施计划并等待批准）：

- **学习目标**：读者通过操作演示要看懂的一个机制是什么？
- **关键问题**：静态内容最难直观看懂的因果关系或误区是什么？
- **角色与单位**：实体有哪些（rank、bucket、tensor、参数等），数据块/消息/计数器如何命名？
- **状态模型**：初始状态、每一步事件、状态变化、不变量、终态分别是什么？
- **同步与时序**：哪些动作同时发生、哪些必须等待、顺序约束由什么保证？
- **边界情况**：第一步、最后一步、空/未就绪/未使用数据、重复循环或 reset 怎样表现？
- **简化说明**：图中省略了什么，哪些量是示意值？

列出状态转换表，并用纸面推演（至少完整走一遍首步、中间步、边界/终态）验证，不要一边写 Vue 一边猜状态。对数据拆分、归约或流转，逐项核算其数量、来源、去向和总量守恒。

## Phase 2：选择最合适的呈现形式

先决定教学任务，再选载体：

- **静态示意图**：布局和关系固定，只需看清结构。
- **逐步状态演示**：阶段或状态转换是核心，提供步骤按钮和说明。
- **播放式动画**：时间流动有帮助时，提供播放 / 暂停；播放速度不应快到读者看不清。
- **可选择数据流**：点击实体、边、单元格或数据块后高亮来源 / 目标、组成员或关联状态。
- **对照视图**：两个过程需要比较时并排展示，而不是把不兼容语义硬塞入单一动画。
- **真实数据图表**：如果呈现的是数据分析图表、热图、统计指标等，先加载并遵循可用的 `dataviz` skill；不把状态示意图误当成真实量化图表。

控制组件范围：一个清晰组件通常比多个小动画更易维护。只有当学习目标、数据模型或操作方式独立时才拆组件。避免过度抽象、没有信息增量的粒子特效、自动播放干扰阅读或动画重述整章所有内容。

## Phase 3：实现交互组件

如果项目使用 VitePress + Vue：

1. 优先在 `docs/.vitepress/components/` 放置自包含 Vue SFC；通过 `docs/.vitepress/theme/index.ts` 注册全局组件，或按项目已有约定导入。
2. 在 Markdown 目标段落附近用组件标签嵌入，并用简短文字说明例子的假设与读者应观察的要点。动画要紧邻解释的概念，不将其孤立放在页面末尾。
3. 将演示状态集中表示（例如当前 step、已触发事件、选中实体），用纯函数或明确映射计算每个实体的展示状态。不要让相同机制在多处用互不一致的硬编码值描述。
4. 提供合适的控制：上一步/下一步、播放/暂停、阶段跳转，以及需要时的重置。循环播放必须处理边界；播放过程不得覆盖用户手动选择。卸载时清除 interval / timeout / listener。
5. 持续呈现步骤编号、阶段名、操作对象、当前数据和结果；使用简洁说明回答“刚才发生什么 / 为什么”。操作应可以暂停、回退或直接跳到关键阶段。
6. 为点击目标设置真实 button / 可聚焦语义、可读的 `aria-label` 和按键可操作性；状态变化使用适当的 `aria-live`，装饰性 SVG 标为 `aria-hidden`。按钮有明确标题和焦点样式。
7. 颜色只是辅助编码：配合文字、形状、边框、标签或箭头；保持可读的亮色 / 暗色主题对比。若做量化或分类图表，使用 `dataviz` skill 的配色验证要求。
8. 适配窄屏：允许局部横向滚动或有计划地重排，不让整页被固定宽度撑开。遵循 `prefers-reduced-motion: reduce`，减少或关闭非必要动画。
9. 数学公式放在普通 Markdown 中由 KaTeX / TexMath 渲染；不要假定 Vue 组件模板中的普通文本会自动成为 LaTeX 公式。组件内需要的短公式可用无歧义文本表达。
10. 避免页面全局 CSS 污染；优先 scoped 样式、语义化 class、主题变量，并沿用项目已有视觉语言。

## Phase 4：验证语义与交互

按复杂度完成下列检查，并如实报告：

### 语义核对（必须）

- 逐步核对状态转换表与实现，确保展示值、提示文字、箭头方向、数据标签互相一致。
- 验证全部 rank / 节点在每个阶段的输入输出；检查总量、shape、归约值或守恒关系。
- 核对顺序约束、并发关系、终态与反向/重置；确认没有重复发送、遗漏数据或不可能状态。
- 检查示意是否掩盖实现差异；将简化假设、适用范围和未展示的机制写进说明。
- 区分源码事实、抽象模型和类比；不要让颜色或运动产生错误因果暗示。

### 工程验证（必须）

- 运行 `git diff --check`；查看最终 diff，确认只改目标文档、所需组件、注册及必要导航。
- 运行项目实际文档构建命令。此仓库若构建内存不足，可用 `NODE_OPTIONS=--max-old-space-size=8192 npm run docs:build`。构建警告要区分既有问题与本次新增问题。
- 检查 SSR / 构建结果中组件有实际渲染，不是只显示未解析的组件标签。
- 能使用浏览器时，打开真实页面并检查：默认状态、每一步、回退、播放 / 暂停、跳转 / 重置、点击选择、窄屏、暗色主题、控制台错误；视觉改动需要看截图或实际页面。
- 若没有浏览器或驱动，执行可行的替代验证（例如构建输出、组件编译、状态转换逐项核对），并明确“未做浏览器点击验证”；不要把工具不可用包装成成功。
- 文档或导航发生变化时，按仓库约定更新索引 / sidebar，并验证真实链接。

## 交付格式

简洁汇报：

1. 增加了什么演示、它帮助理解哪个机制；
2. 涉及哪些可点击文件；
3. 完成了哪些语义、构建和浏览器验证；
4. 哪些验证因环境限制未做，以及实际存在的 warning / limitation。

只有实际运行并成功的检查才能写为通过。不要提交或推送，除非用户明确要求。
