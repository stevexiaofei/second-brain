# 并行文件系统

## 一句话理解

并行文件系统（PFS）可以理解成：**让很多机器一起提供一个看起来像普通文件系统的共享存储**。它保留了你熟悉的 `path / file / directory / permission` 这些语义，但内部把数据和元数据拆开，在多台机器上并行处理。

## 为什么会有并行文件系统

普通文件系统单机就够用，但当你遇到下面这些场景，单机就不行了：

- 多个训练任务同时读海量数据
- 一个文件太大，单节点带宽不够
- 一个目录里有几百万个文件
- 多台计算节点需要共享同一份数据
- 需要比 NFS 更高的吞吐和更强的扩展性

这时就需要 PFS。

## 它想解决什么

PFS 主要要解决四类问题：

1. **并发读写**：很多客户端同时访问
2. **大文件吞吐**：把一个文件拆成条带并行读写
3. **共享语义**：让多个计算节点看到一致的文件系统视图
4. **元数据扩展**：目录、权限、inode、rename 等操作不能卡死

## PFS 的基本架构

```text
客户端
  │
  ├─ 元数据路径：查文件名、权限、大小、布局
  │
  └─ 数据路径：直接和多个数据服务器并行传输
        │
        ├─ 元数据服务器（MDS）
        └─ 数据服务器（OST / OSD / Chunk Server）
```

## 先理解两个最关键的概念

### 1）元数据和数据分离

- **元数据**：文件名、目录、权限、时间戳、文件大小、块位置
- **数据**：真正的字节内容

这样做的原因很简单：
- 你查“这个文件在哪”不应该每次都把文件内容读一遍
- 你修改“目录结构”不应该影响所有数据块

### 2）条带化（Striping）

一个大文件被切成很多条带，分别放到多个数据服务器上。

这样客户端在读一个文件时，可以并行向多个节点取数据，从而提高吞吐。

```text
file = [chunk1][chunk2][chunk3][chunk4]
         │       │       │       │
        OST1    OST2    OST3    OST4
```

## 条带化为什么有用

如果一个训练文件很大，比如视频、点云、checkpoint：
- 单节点读取太慢
- 网络带宽不能充分利用
- 多节点同时访问也可能争抢同一台机器

条带化可以让：
- 数据分散存放
- 读取并行发生
- 聚合带宽提升

## 条带大小与条带数

### 条带大小（stripe size）

每一条带有多大，比如 1MB、4MB、16MB。

### 条带数（stripe count）

一个文件分布到多少个数据服务器。

### 怎么理解它们

- 条带太小：元数据和调度开销变大
- 条带太大：并行度不足
- 条带数太多：小文件不划算，锁和管理开销上升

所以 PFS 配置经常要按数据类型调：
- 大文件：更大条带、更高并行度
- 小文件：尽量少条带，甚至单条带

## POSIX 语义是什么

PFS 最吸引人的地方之一，是它通常尽量模拟 POSIX 文件系统语义。

这意味着：
- `open/read/write/close` 的行为符合程序预期
- 目录、权限、rename 等操作较自然
- 传统应用无需大改就能迁移

但代价是：
- 语义越强，系统越复杂
- 元数据协调成本越高
- 高并发下更容易遇到锁和一致性问题

## 元数据服务器为什么是瓶颈

很多 PFS 的瓶颈不是“读数据”，而是“管理数据”。

因为这些操作太多了：
- 创建文件
- 删除文件
- 修改权限
- 列目录
- rename
- stat
- 打开关闭

这些都要访问元数据。

如果一个目录里有几百万个小文件，元数据服务就会很痛苦。

## 锁为什么重要

为了保证多个客户端不会把同一份数据写乱，PFS 必须用锁。

锁的作用：
- 控制并发写
- 协调缓存一致性
- 防止多个客户端同时修改同一范围的数据

但锁本身也会带来问题：
- 频繁锁竞争
- 锁回调开销
- 高并发写热点

所以“锁”是 PFS 性能与正确性的核心平衡点。

## 客户端缓存

PFS 通常允许客户端缓存元数据和数据，这样可以减少远程访问。

但缓存一旦存在，就会出现：
- 谁先改了文件
- 其他客户端什么时候知道
- 缓存什么时候失效

所以 PFS 往往会搭配：
- 锁
- 回调
- lease
- 版本号

来维护一致性。

## 常见的 PFS 系统

| 系统 | 元数据 | 数据布局 | 特点 |
|---|---|---|---|
| Lustre | 中心化 MDS | OST 条带化 | HPC 常见，高吞吐 |
| GPFS / Storage Scale | 分布式元数据 | 条带化 + 复制 | 企业级、强一致、可扩展 |
| CephFS | 分布式 MDS | RADOS 对象 | 开源生态强，和 Ceph 一体 |
| BeeGFS | 分布式元数据 | 条带化 | 容易部署，性能不错 |

## PFS 适合什么

### 适合

- HPC
- 大规模训练数据集
- 大文件并发读
- 共享工作区
- checkpoint 读写

### 不太适合

- 超多小文件频繁创建删除
- 随机小 IO 很重的业务
- 频繁 rename / append 的应用

## 为什么 AI 训练特别依赖 PFS

AI 训练经常需要：
- 多个 GPU 节点同时读同一数据集
- 读取速度跟得上 GPU 消耗
- checkpoint 周期性大吞吐写入

所以 PFS 常常作为：
- 对象存储之上的加速层
- 训练节点共享工作区
- 热数据承载层

## 小文件问题

小文件多的时候，真正慢的往往不是磁盘，而是元数据。

问题表现：
- 目录遍历慢
- `stat` 很慢
- 启动训练集很慢
- 大量文件打开关闭拖慢吞吐

常见解决思路：
- 打包成大文件（TFRecord / WebDataset / LMDB 等思路）
- 减少目录层级
- 预生成 manifest
- 缓存元数据

## 你应该记住的一个公式化直觉

> 大文件看带宽，小文件看元数据。

这是理解 PFS 的关键。

## 与对象存储的关系

- 对象存储适合“海量、低成本、弱语义”
- PFS 适合“POSIX 友好、共享访问、训练加速”

很多现代系统会把两者组合起来：
- 对象存储作为底座
- PFS 作为上层热路径
- 本地盘/内存作为最后一级缓存
