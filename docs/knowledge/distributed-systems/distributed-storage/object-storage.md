# 分布式对象存储

## 一句话理解

对象存储可以理解成一个**超大规模、扁平命名空间的键值仓库**：你通过 key 找到 object，而不是通过路径在本地文件系统里一层层向下走。它的强项是**海量扩展、低成本、易管理**，弱项是**不像本地文件系统那样灵活**。

## 对象存储长什么样

对象存储最核心的三个概念：

- **Bucket**：桶，逻辑上的容器
- **Object**：对象，真正保存的数据
- **Key**：对象名字，通常长得像 `a/b/c.jpg`

```text
bucket = my-dataset
key    = train/scene_001/frame_000123.jpg
object = { data, metadata, version }
```

> 目录只是 key 的前缀，并不一定是真正的文件夹。

## 为什么对象存储适合大规模数据

对象存储最适合下面这种数据：

- 写一次，读很多次
- 文件很多，整体很大
- 不太需要频繁原地修改
- 更看重容量、成本和水平扩展

这也是为什么数据湖、备份、日志、训练数据集常常放对象存储。

## 它和文件系统最大的区别

| 维度 | 对象存储 | 文件系统 |
|---|---|---|
| 命名空间 | 扁平 | 树状目录 |
| 修改方式 | 通常是整对象写入 | 可以局部修改 |
| 访问协议 | HTTP / S3 API | POSIX / NFS / SMB |
| 元数据 | 对象级别 | 文件 + 目录 + inode |
| 扩展性 | 非常强 | 受元数据限制更明显 |
| 典型场景 | 数据湖、归档、训练数据 | 工作目录、共享文件、HPC |

## 对象存储的写路径

一个简单的写入过程通常是：

1. 客户端发起 `PUT Object`
2. 服务端检查权限、桶策略、对象名
3. 如果对象很大，可能走分片上传
4. 数据写入后端存储节点
5. 写入元数据索引和版本信息
6. 返回成功

这个过程里，真正困难的是：
- 怎么让对象可靠保存
- 怎么让元数据和数据一致
- 怎么处理失败重试
- 怎么避免部分写入留下脏数据

## 读路径

1. 客户端发起 `GET Object`
2. 服务端查元数据和位置
3. 从存储节点取回数据
4. 校验完整性
5. 返回给客户端

对于读来说，最重要的是：
- 读到的是不是最新版本
- 是否发生了副本切换
- 是否需要重试和修复

## 一致性模型

对象存储的历史上经常是最终一致，但现在很多主流系统已经做到**写后读强一致**，至少在单区域内是这样。

你要区分三个层次：

### 1）写后读一致（Read-after-write consistency）

写成功后，立刻读应该能看到。

### 2）列表一致性（List consistency）

列目录/列桶时，刚写入的对象是否立刻可见。

### 3）跨区域复制一致性

跨地域复制通常还是最终一致，因为距离远、延迟高、链路更复杂。

## 为什么对象存储常常是“扁平”的

因为扁平命名空间更容易水平扩展。

如果系统真的把“目录”当成树结构处理，那么：
- 深层目录遍历会慢
- 目录锁会复杂
- rename/move 会贵
- 元数据压力更大

所以很多对象存储会把“目录”简化成 key 前缀。

## Multipart Upload：大对象上传的关键机制

大文件直接传输很容易失败，所以对象存储会支持分片上传：

1. 先创建一个上传会话
2. 把大对象切成多个 part
3. 每个 part 可以并发上传
4. 全部 part 成功后再提交合并
5. 失败则可以中止会话并重传部分分片

好处：
- 支持断点续传
- 支持并发
- 避免单次超大请求失败导致全盘重来

## Versioning：版本管理

开启版本管理后，同一个 key 可以有多个版本。

这很重要，因为它能：
- 防止误删导致永久丢失
- 支持回滚
- 支持审计和追踪

对象存储里的“删除”很多时候只是增加一个删除标记，而不是立刻物理清除所有历史版本。

## Lifecycle：生命周期管理

生命周期策略是对象存储降本的重要手段。

常见规则：
- 多少天后转到低频存储
- 多少天后归档
- 多少天后删除
- 某些前缀的对象定期过期

这使得对象存储特别适合：
- 日志
- 备份
- 训练原始数据
- 归档数据

## 访问控制

对象存储的权限控制通常包括：

- IAM / STS
- Bucket Policy
- ACL
- 临时签名 URL

权限设计的关键是：
- 谁能读
- 谁能写
- 谁能列举
- 谁能删除
- 谁能管理生命周期

## 完整性校验

对象存储必须非常重视数据完整性。

常见做法：
- ETag 或校验和
- 分片校验
- 后台 scrub
- 读时校验
- 元数据和数据双检查

因为对象一旦损坏，往往是大规模、批量、长期保存的数据，出问题代价很高。

## 对象存储为什么常和训练数据绑定

AI 训练数据通常有这些特征：

- 总量大
- 读取多于修改
- 允许稍弱的文件语义
- 强调成本与规模

所以对象存储很适合做“数据底座”，再配合：
- 并行文件系统
- 本地缓存
- 预取系统
- 训练加速层

## 初学者最容易误解的点

### 1）把对象存储当成磁盘

不对。它不是块设备，也不是真文件系统。

### 2）把“目录”当真实目录

很多时候目录只是 key 前缀。

### 3）把 list 当作便宜操作

list 可能很贵，尤其在海量对象场景。

### 4）以为对象存储适合频繁小更新

通常不适合。对象存储更擅长整对象替换，而不是局部原地修改。

## 什么时候不要直接用对象存储

- 需要强 POSIX 语义
- 需要大量 rename / append
- 需要极低延迟小 IO
- 需要频繁随机修改同一文件

这时更适合：
- 块存储
- 并行文件系统
- 本地盘缓存
