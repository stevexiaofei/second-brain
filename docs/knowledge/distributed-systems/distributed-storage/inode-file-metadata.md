# inode：文件身份、元数据与数据定位

## 一句话理解

**inode 描述一个文件对象的身份、属性和数据布局；目录项把名字关联到 inode；fd 是进程访问已打开文件的句柄。它们不是同一个东西。**

理解这几个对象，才能解释为什么改名不必复制文件内容、硬链接能共享内容、删除文件后空间未必立即释放，以及为什么大文件吞吐不能代表小文件性能。

::: info 适用范围
本文以 Linux VFS 和常见类 Unix 文件系统为主。磁盘格式、内核数据结构和网络文件系统协议不是同一层；下文的图是职责模型，不是所有文件系统通用的固定实现。命令示例面向 Linux，未在真实 Linux 文件系统或 NFS/CephFS 集群执行验证。
:::

## 1. 先分清“名字”“文件对象”和“打开状态”

假设有文件 `/data/a.txt`：

```text
命名空间：父目录中的记录
  名字 "a.txt" ────────────────→ inode #100
                                  ├── 类型、权限、uid/gid
                                  ├── 大小、时间、硬链接计数
                                  └── 数据布局或关联的映射结构
                                            │
                                            ▼
                                      文件内容 / 后端数据

访问关系：当前进程
  fd 3 → 打开文件对象（当前偏移、打开标志）
             └── 关联该文件路径和 inode #100
```

| 对象 | 主要回答的问题 | 不要混同为 |
|---|---|---|
| 路径名 | 从哪个目录出发，沿哪些名字找到对象？ | 文件的永久身份 |
| 目录中的记录 | 父目录中的某个名字对应哪个对象？ | 文件内容 |
| dentry | 内核中“父目录 + 名字”的查找关系是什么？ | 磁盘目录记录本身 |
| inode | 文件对象的属性、身份和布局是什么？ | 文件名、fd、全部内容 |
| 打开文件对象（open file description；Linux 中通常对应 `struct file`） | 这次打开的偏移和状态是什么？ | inode 本身 |
| fd（file descriptor） | 进程用哪个整数访问打开文件对象？ | inode 号、物理地址 |
| page cache | 哪些文件内容已经在内核内存里？ | inode 元数据缓存 |

### 磁盘目录记录不等于内核 dentry

在 ext4 等典型本地文件系统中，目录内容包含“名字 → inode 编号”的记录。Linux VFS 的 **dentry 是内存对象**，缓存路径分量的查找结果，关联父目录、名字以及可能存在的 inode。

dentry 甚至可以表示“这个名字目前不存在”，称为 **negative dentry**。因此不能把每个 dentry 都画成必然指向某个已存在文件，也不能认为把目录持久化就是把 dentry 内存对象直接写盘。

### 磁盘 inode 不等于内存 inode

- **持久化表示**：具体文件系统保存文件元数据的格式，例如 ext4 的磁盘 inode 记录及其关联结构。
- **内存表示**：Linux VFS 的 inode 对象及文件系统扩展状态，用于权限、大小、缓存和操作接口等。

网络文件系统客户端也有 VFS inode，但不代表客户端磁盘上必然存在一份与服务端格式相同的 inode 表。**inode 是通用抽象，不是一种所有系统统一采用的磁盘布局。**

## 2. inode 通常记录哪些信息？

| 类别 | 常见信息 | 作用与边界 |
|---|---|---|
| 类型 | 普通文件、目录、符号链接、设备、FIFO、socket 等 | inode 不只属于普通文件 |
| 权限与所有者 | mode、uid、gid，以及 ACL/扩展属性的关联信息等 | 访问检查还可能涉及路径目录权限和其他安全机制 |
| 文件大小 | 逻辑字节长度 | 不等于实际分配空间 |
| 时间 | atime、mtime、ctime；部分系统还有 birth time | 更新规则受文件系统和挂载选项影响 |
| 硬链接数 | `st_nlink` | 对普通文件可理解为仍有多少个硬链接名称，不能拿它当打开 fd 数 |
| 数据布局 | 块指针、extent 树或其他布局结构的引用 | 不必直接列出每个最终物理地址 |

有些属性并不完全内联在 inode 记录里，而是通过扩展属性、其他元数据树或服务端状态维护。**“inode 描述文件”不等于“所有相关信息都塞进一个固定大小结构”。**

### 文件名通常不在 inode 中

同一个 inode 可以有多个硬链接名字：

```text
父目录中的 "a.txt" ──┐
                     ├──→ inode #100 → 同一文件内容
另一个目录的 "b.txt" ─┘
```

因此 inode 不需要选一个名字作为自己的唯一身份；完整路径更不是通常保存在 inode 里的属性。

### 三个时间不要混淆

- **atime**：访问时间；`noatime`、`relatime` 等策略会影响更新，不是每次读都必须同步写一个新时间。
- **mtime**：文件内容修改时间。
- **ctime**：inode 状态变化时间，**不是 creation time**。写内容、改大小、权限、所有者或链接关系等可能影响它。

例如 `chmod 600 file.txt` 通常改变 ctime 而不改变 mtime；追加内容通常同时改变 mtime 和 ctime。部分系统通过 `statx` 等接口提供 birth time，不能用 ctime 替代。

### inode 不等于“指向文件内容的指针”

inode 不是只有一个数据地址。它还要描述类型、权限、大小和生命周期信息；特殊类型也不一定有普通文件意义上的内容数据块。例如设备文件记录设备身份，短符号链接或少量文件内容在部分文件系统中还可能内联保存。

## 3. 逻辑 offset 如何找到实际数据？

应用调用：

```python
n = os.preadv(fd, [buf], offset)
```

其中 `offset` 是**文件内部的逻辑字节位置**，不是磁盘块地址。

```text
文件逻辑范围
  → inode 关联的缓存与布局信息
  ├── 内容已在 page cache：复制到用户缓冲区
  └── 需要后端数据：查布局映射
        ├── 本地文件系统：文件块 → extent / 块映射 → 块设备
        └── 分布式文件系统：文件范围 → 条带 / 对象 → 存储节点
```

- 传统文件系统可能使用直接块指针和多级间接块。
- ext4 等现代文件系统常用 **extent**，用一段范围映射描述连续的文件块和后端块，而不是逐块存一根指针。
- 块设备下面还可能有 LVM、RAID、虚拟磁盘或 SSD 的地址转换，因此文件系统块号也不等于最终 NAND 单元地址。
- CephFS 等系统通过文件布局、对象编号和放置机制定位内容，不是让应用把 inode 号直接当成 OSD 地址。

### 逻辑大小不等于实际占用

稀疏文件的某些逻辑范围没有实际分配数据块，称为 hole（洞）。读取洞可以直接得到零，不必读出同等大小的后端数据。

因此 `stat` 的逻辑大小、实际分配块数，以及压缩、去重、副本之后的后端占用是不同口径。Linux `stat` 的 `st_blocks` 以 512 字节为计数单位，不应直接等同于文件系统块数；具体统计语义仍与文件系统有关。

这解释了[磁盘 I/O 压测](../../engineering/profiling/08-disk-io-benchmark.md)为什么要先完整写入测试文件：仅扩展文件长度再随机读，可能主要读到洞，虚高逻辑 IOPS。

## 4. 从 `open()` 到读写：inode 在哪里参与？

### `open()`：名字变成 fd

```text
路径查找：逐级目录、符号链接、挂载点
  → 使用 dentry / inode 缓存，必要时访问元数据后端
  → 检查权限、执行创建或截断等打开语义
  → 建立打开文件对象
  → 在当前进程 fd 表中分配整数索引
```

`O_CREAT` 允许创建不存在的文件；`O_TRUNC` 在适用的可写打开中截断已有文件。**打开文件不等于把全部文件内容读入缓存；截断也不等于写好目标大小的数据。**

### `read/write`：通过打开文件对象访问文件

后续主要通过 fd 找到打开文件对象及关联 inode，不必每次从根目录重新解析完整路径。网络文件系统仍可能做必要的属性或一致性校验。

普通文件 buffered I/O 中：

- **读**：根据文件身份和逻辑范围查询 page cache；未命中才需要向下取数据。
- **写**：修改缓存内容并标记 dirty；可能更新大小、时间和空间布局；返回不等于已经持久化。
- **同步**：`fsync(fd)` 推进文件数据和相关元数据的持久化，不单独保证父目录名称更新也已持久化。

### inode cache 命中不等于文件内容命中

可能已经知道文件的大小、权限和布局，但内容不在 page cache，读取仍需访问后端。反过来，内容已缓存，也不表示所有路径查找和网络元数据校验都能省略。

### 偏移不属于 inode 的全局读取游标

```text
独立 open("a.txt") → 打开对象 A，偏移 0 ──┐
                                       ├──→ 同一个 inode
独立 open("a.txt") → 打开对象 B，偏移 0 ──┘
```

- 两次独立 `open()` 通常具有独立偏移，但可能共享文件内容缓存。
- `dup()` 得到的 fd 共享打开文件对象，因此共享当前偏移。
- `read/write` 使用并推进当前偏移；`preadv/pwrite` 使用显式 offset，不推进它。显式 offset 不负责防止重叠写。

Python 的参数形式也要区分：

```python
import os

fd = os.open(path, os.O_RDONLY)  # path 是要读取的文件路径
try:
    data = os.read(fd, 4096)    # 第二个参数是字节数，返回 bytes
finally:
    os.close(fd)

# 若想读入已有缓冲区，另一次打开后可使用：
fd = os.open(path, os.O_RDONLY)
try:
    buf = bytearray(4096)
    n = os.readv(fd, [buf])     # 返回实际填充字节数；有效数据为 buf[:n]
finally:
    os.close(fd)
```

这两个片段演示接口差异，不是“恰好读满 4096 字节”的保证；短读和 EOF 需要按业务处理。不能把 C 的 `read(fd, buf, count)` 机械写成 Python 的 `os.read(fd, buf)`。

### 动画：同一 inode，为什么偏移可以独立或共享？

先走完打开流程，再切换“再次独立 open”和“dup 共享打开对象”，跳到最后查看 fd 表：独立打开关联同一 inode 但偏移独立；`dup` 共享打开文件对象，因此通过一个 fd 读取也会改变另一个 fd 观察到的当前偏移。可以点击角色盒子查看 inode、dentry 和 fd 的职责。

同一组件还能切到读取、写入、同步和压测计时；各组适用范围与简化假设都在组件底部。完整数据路径说明见[磁盘 I/O 压测](../../engineering/profiling/08-disk-io-benchmark.md)。

## 5. 硬链接、符号链接与改名

### 硬链接：增加名字，不复制文件对象

对一个普通文件执行 `ln a.txt b.txt`，两个名称指向同一 inode。修改该 inode 的内容，两条路径都可见；删除一个名称只会减少硬链接计数。

这里说的是**原地修改同一文件对象**。如果编辑器先写临时文件，再用 rename 替换 `a.txt`，`a.txt` 会指向新 inode，`b.txt` 仍指向旧 inode；不能笼统保证“所有修改方式都会反映到所有原硬链接”。

普通硬链接要求位于同一文件系统，且不能跨不支持该操作的挂载边界；通常不允许对目录创建普通硬链接。创建硬链接不额外创建目标文件 inode，但目录记录本身仍有空间和元数据开销。

### 符号链接：独立对象，保存目标路径

```text
a.txt    → inode #100 → 文件内容
link.txt → inode #200 → 路径字符串 "a.txt"
```

符号链接有自己的 inode，访问时通常继续解析目标路径。相对路径以**符号链接所在目录**为基准，不是任意调用进程的当前目录。

| 特性 | 硬链接 | 符号链接 |
|---|---|---|
| 文件对象 | 与目标共享 inode | 链接有自己的 inode |
| 保存目标路径 | 否 | 是 |
| 可否跨文件系统指向目标 | 不能用普通硬链接实现 | 可以 |
| 原目标名称删除 | 其他硬链接仍有效 | 若路径已不存在，则成为悬空链接 |

### rename：改名称关系，不必搬数据

同一文件系统内改名通常保留源文件 inode，不复制全部文件内容。如果目标名已经存在且允许替换，目标名称转而指向源 inode；此前打开旧目标的 fd 仍关联旧文件对象。

这也是“路径相同不代表文件对象相同”的重要例子：**已打开 fd 跟随文件对象，而不是每次读时重新跟随同一路径的新目标。** 跨文件系统的 `rename` 通常报 `EXDEV`；命令行 `mv` 可能改为复制再删除，不能据此宣称跨文件系统移动也不搬数据。

## 6. 为什么 `rm` 后空间可能没有释放？

对普通文件，`unlink` 删除的是目录中的名称，不是立即销毁所有引用：

```text
原来：名字 → inode ← 打开文件对象 ← fd

删除最后一个名字后：
       link count = 0
       inode ← 打开文件对象 ← fd

最后的打开/映射等存活引用释放后：
       文件系统才可以回收 inode 和相关空间
```

因此日志文件可能已经没有可见文件名，但进程仍能通过旧 fd 继续写，空间暂时不能回收。除了 fd，内存映射等也可能延长文件生命期，不能把“最后一个 fd 关闭”当作所有情形下立即回收的充分条件。

Linux 排查可用 `lsof +L1`：`+L1` 筛选链接数小于 1 的打开文件。输出受权限和文件系统实现影响。NFS 客户端还可能把打开但被删除的文件临时改名为 `.nfs...`，不能假定所有网络文件系统都完整复现本地文件的可见细节。

**不要直接截断仍被使用的文件来“释放空间”**；应先确认所属进程和业务约束，采用受支持的日志轮转/重新打开流程。

## 7. inode 为什么影响小文件性能和容量？

### 目录本身也有 inode

目录也是文件系统对象，有自己的权限、所有者和目录数据。路径解析是在目录层级中逐步查找名字；dentry/inode 缓存减少重复查找成本，但并不消除目录和元数据本身。

目录的硬链接计数有与父子目录关系相关的传统语义，具体文件系统还可能采用特殊计数策略，不能直接用“普通文件有几个名字”的例子推算所有目录的 `st_nlink`。

### 小文件会放大元数据成本

创建、打开、删除大量小文件，可能涉及 inode 分配、目录记录更新、权限检查、缓存查找、日志事务、锁竞争和网络元数据请求。具体步骤会被缓存、延迟分配和事务批处理改变，不是每次都一条一条独立落盘。

所以“一个大文件上 4 KiB 随机读”不等于“每次打开一个新的 4 KiB 小文件”。前者主要测试数据范围访问；后者还包括大量文件生命周期和命名空间操作。参见[元数据与性能瓶颈](./metadata-and-performance.md)。

### 字节空间与 inode 资源是两种约束

```bash
df -h   # 文件系统容量
df -i   # 文件系统报告的 inode 统计
```

某些文件系统可能还有很多数据块空间，却没有可分配 inode，导致创建文件报 `ENOSPC`。

但不要泛化为所有文件系统都在格式化时分配固定 inode 总数：ext4 的典型配置与 XFS 等动态分配机制不同，网络文件系统的统计也可能不完整。`ENOSPC` / `EDQUOT` 还需要结合块空间、inode、用户配额和文件系统元数据限制排查，而不是只看一个 `df` 数字。

## 8. 如何观察 inode？

以下命令以实际存在的 `file.txt` 为例；inode 号由所在文件系统分配，不要照抄示意数字判断身份。

```bash
ls -li file.txt        # inode 编号、权限、链接数等
stat file.txt         # 大小、设备号、inode、链接数、时间
stat -L link.txt      # GNU stat：跟随符号链接查看目标
lsof +L1             # 查找已无硬链接名称但仍打开的文件
```

Python 中可比较：

```python
import os

st = os.stat(path)              # 通常跟随符号链接
identity = (st.st_dev, st.st_ino)
link_st = os.lstat(symlink_path) # 查看符号链接自身；symlink_path 为链接路径
```

设备号与 inode 号常用于运行期间、当前文件系统视图下识别文件，但不是永久全局 UUID：inode 号在删除回收后可以重用，网络、叠加文件系统和挂载视图也可能增加身份判断的复杂性。

## 9. 本地、NFS、CephFS：抽象相通，实现不同

| 场景 | 文件身份和元数据如何维护？ | 数据如何定位？ |
|---|---|---|
| ext4 / XFS 等本地文件系统 | 本机 VFS 对象与文件系统持久化结构协作 | 通过文件块映射访问块设备 |
| NFS | 服务端文件对象/文件句柄与客户端缓存协作；客户端也有 VFS inode | 客户端向服务端请求数据；不能把客户端 inode 号直接当服务端物理块号 |
| 原生 CephFS | MDS 管理命名空间、文件元数据和客户端能力，客户端缓存协作 | 依据文件布局和集群映射访问 OSD 上的对象，不要求内容全部经 MDS 转发 |

inode 抽象没有消除网络延迟、复制和一致性问题。参见[NFS 部署与挂载](./nfs-deployment-and-mount.md)、[CephFS 部署与挂载](./cephfs-deployment-and-mount.md)。

## 10. 与磁盘压测 API 对照

| API | inode / 命名空间相关活动 | 测量时不要误读 |
|---|---|---|
| `os.open` | 查找、权限检查，可能创建 inode 或截断文件 | 不等于读入文件内容 |
| `os.write` / `os.pwrite` | 修改内容，可能更新大小、时间和空间布局 | 写返回不等于 inode 和内容均已持久化 |
| `os.readv` / `os.preadv` | 根据文件身份、逻辑范围和缓存定位数据 | offset 不是物理地址；缓存命中未必访问后端 |
| `os.fsync` | 推进文件内容及相关元数据的同步持久化 | 不单独保证父目录项同步，也不等于驱逐 inode/page cache |
| `os.rename` | 更新目录中的名称关系；在脚本中复用同一个已初始化文件 | 是元数据操作，不是复制整份测试数据 |
| `os.close` | 释放 fd 和相关引用 | 不是通用持久化屏障，也不必立即回收 inode |

压测脚本在同一 scratch 目录内把完整写入的顺序文件改名后，继续做随机覆盖读写。因此它没有把海量小文件的 inode/目录生命周期负载纳入这些 phase；详细计时边界见[磁盘 I/O 压测](../../engineering/profiling/08-disk-io-benchmark.md)。

## 我的理解

以下是组织心智模型的个人归纳，不是另一套文件系统实现规则：

- **名字是入口，inode 是对象，fd 是已经打开的访问关系**。改名和路径替换，要分清究竟改变了哪一层。
- **元数据缓存与内容缓存分开看**。知道文件是谁，不等于数据已在内存；读不到文件名，也不等于旧 fd 已失效。
- **数据面与元数据面分开测**。大文件吞吐、单文件随机读写、海量文件的创建和打开，解决的不是同一个性能问题。

## 常见误区

1. **inode 就是文件名**：普通文件的硬链接证明名字与对象可以多对一。
2. **inode 就是一根数据指针**：类型、权限、大小、链接和布局都是它的重要职责。
3. **ctime 就是创建时间**：它是状态变化时间。
4. **fd 就是 inode 号**：fd 是进程中的整数句柄，偏移主要属于打开文件对象。
5. **删除名字立即释放空间**：还要考虑其他硬链接、打开引用、内存映射和文件系统回收机制。
6. **inode 号永久唯一**：只能在明确文件系统视图和生命周期内使用，不是全局永久身份。
7. **文件 `fsync` 自动同步文件名**：目录更新仍有独立的持久化要求。
