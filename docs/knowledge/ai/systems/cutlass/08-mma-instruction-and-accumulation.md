# MMA 指令语义：D = A×B + C 与累加方向

## 一句话理解

mma 不是"乘法指令"，而是**乘加指令**：累加器输入 `C` 就写在指令的操作数里，硬件一次完成 $D = A \times B + C$。这个语义决定了 mma 的两类组合方式——**K 方向是共用一个累加器的串行依赖链，M/N 方向是互不相关的独立链**。前者不能拆给不同线程，后者可以。

## 为什么重要

- 它解释了 `make_tiled_mma` 里那个"为什么 K 维不做线程扩展"的问题。
- 它解释了为什么 K 维扩展**不带来并行度**，只是把累加拆成多步（见 [03](./03-cute-tiled-mma.md)）。
- 它解释了 CuTe 的编程惯例：`gemm()` 的 `C` 兼作输入与输出，K 主循环前必须 `clear(tCrC)`。
- 忘记清累加器是 GEMM 的典型 bug，根因就在这条指令语义。

## 指令语义

以 SM80 的 `m16n8k8` FP32 累加 + BF16 输入为例，PTX 形式：

```text
mma.sync.aligned.m16n8k8.row.col.f32.bf16.bf16.f32
    {d0,d1,d2,d3}, {a0,a1}, {b0}, {c0,c1,c2,c3};
```

| 操作数 | 作用 | 每线程寄存器数 | 推导 |
|---|---|---|---|
| `a0,a1` | A 分片 | 2 个（4 个 bf16） | $16\times8 / 32 = 4$ 个元素 |
| `b0` | B 分片 | 1 个（2 个 bf16） | $8\times8 / 32 = 2$ 个元素 |
| `c0..c3` | **累加器输入** | 4 个（4 个 f32） | $16\times8 / 32 = 4$ 个元素 |
| `d0..d3` | **累加结果输出** | 4 个（4 个 f32） | 与 C 同形 |

语义恒为：

$$D = A \times B + C$$

**注意 `C` 是一个必须提供的操作数**，不是可选优化。所以"mma 内部会不会累加"这个问题的答案是：永远会。

## 逐条读 SASS

原文（tile `32x32x16`，ValExpand `(1,1,2)`）的 SASS：

```text
LDG.E R4,  [R14.64]         ┐
LDG.E R5,  [R16.64]         │ k=0..7 的 A 分片 → 喂给第一条的 A 操作数
LDG.E R6,  [R18.64]         │ k=0..7 的 B 分片
LDG.E R2,  [R14.64+0x10]    ┐
LDG.E R3,  [R16.64+0x10]    │ k=8..15 的 A 分片 → 喂给第二条的 A 操作数
LDG.E R11, [R18.64+0x10]    │ k=8..15 的 B 分片

HMMA.1688.F32.BF16 R4, R4,  R6,  RZ
HMMA.1688.F32.BF16 R4, R2,  R11, R4

F2FP.BF16.F32.PACK_AB R5, R5, R4
F2FP.BF16.F32.PACK_AB R7, R7, R6
STG.E [R12.64], R5
STG.E [R2.64],  R7
```

SASS 中 `HMMA.1688.F32.BF16 Rd, Ra, Rb, Rc` 的操作数是**寄存器组**（D/C 各 4 个、A 2 个、B 1 个）。逐条拆：

| | D（目的组） | A（组） | B | **C（累加器输入）** | 语义 |
|---|---|---|---|---|---|
| 第一条 | `R4..R7` | `R4,R5` | `R6` | **`RZ`** | $D = A_0 B_0 + 0$ |
| 第二条 | `R4..R7` | `R2,R3` | `R11` | **`R4..R7`** | $D = A_1 B_1 + D$ |

三个值得注意的细节：

1. **第一条用 `RZ` 当 C**。`RZ` 是硬件恒零寄存器，用它作累加初值等价于"清零累加器"，**不需要额外的 MOV 指令**。这也是 SASS 里看不到显式清零的原因。
2. **第二条的 D 和 C 是同一组寄存器 `R4..R7`**，即原地累加——这是硬件层面"接着上一次的结果继续加"的标准写法。
3. **第一条的 A 操作数 `R4,R5` 和 D 组 `R4..R7` 重叠**。SASS 允许源/目的操作数重叠，硬件保证先读后写：`R4,R5` 作为 A 被读走之后才被 D 覆盖。所以这个写法是安全的，不是笔误。

顺带把 epilogue 也读通：D 组的 4 个 f32 累加器 `R4..R7` 经两条 `F2FP...PACK_AB` 打包成 2 个 bf16 寄存器（`R5 = pack(d1,d0)`、`R7 = pack(d3,d2)`），再由 2 条 STG 写回——这也解释了"K 扩展后 STG 仍然只有 2 条"。

## 累加方向：K 是串行链，M/N 是独立链

这是最容易混的地方。把一次 `gemm()` 展开后的多条 mma 按方向分类：

```text
              N →
        ┌──────────┬──────────┐
   M    │  D(0,0)  │  D(0,1)  │   ← 不同 (m,n)：不同累加器
   ↓    ├──────────┼──────────┤      彼此独立，可并行发射，
        │  D(1,0)  │  D(1,1)  │      用来掩盖延迟
        └──────────┴──────────┘
             ↑
      同一格内沿 K 的多条 mma 共用同一个 D
      → 串行依赖链（前一条的 D 必须喂给后一条的 C）
```

| 扩展方向 | 累加器关系 | 对并行度的影响 |
|---|---|---|
| **M / N 扩展** | 各自对应**不同**的 $D$ 元素 | 相互独立 → **提高并行度** |
| **K 扩展** | 共用**同一个** $D$ | 串行依赖链 → **不增加并行度** |

推论：如果只沿 K 扩展，付出的寄存器代价换不来并行收益，只是把一个长累加拆成多步。所以实际 kernel 里**必须同时有 M/N 方向的独立链**，用它们的并行度去掩盖 K 链的延迟。

## 为什么 K 方向不能做线程扩展

`make_tiled_mma` 的第一个参数 `MMAThrLayout` 的 K 维一般取 1，原因就在累加器归属：

$$\underbrace{D[m,n] = \sum_{k} A[m,k]\,B[k,n]}_{\text{K 是需要归约的维度}}$$

累加器 $D[m,n]$ **由某一个线程独占**（它是一组私有寄存器）。如果把 K 拆给不同线程：

- 同一个 $(m,n)$ 的部分和会散落在多个线程的寄存器里；
- 每步之后都必须做**跨线程归约**（warp shuffle 或经 SMEM），代价极高；
- 而 $m,n$ 不同就是不同的输出元素，天然无需归约，拆线程是免费的。

所以规则很清晰：**可拆的是 M/N（输出维），不可拆的是 K（归约维）**。

## 与 CuTe API 的对应

`gemm()` 的签名把这条语义直接搬到了接口上：

```cpp
gemm(tiled_mma, tCrC, tCrA, tCrB, tCrC);
//               ↑ 既是初始累加器 C，又是结果 D
```

- `tCrC` 同时出现在 `C` 位置和 `D` 位置，对应指令里 `D = A×B + C` 的原地累加；
- K 主循环开始前要先 `clear(tCrC)` 把累加器清零（编译后可能被折叠成 `RZ`）；
- 每轮 K 迭代调用一次 `gemm()`，都是在已有累加值上继续加。

**这也是"忘记清零累加器"成为典型 bug 的原因**：如果 `tCrC` 里残留上一次的输出，后续所有 `gemm()` 都会在错误初值上累加。

## 我的理解

（以下为个人理解）

- 把 mma 记成"乘加"而不是"乘法"，很多设计决策就顺了：累加器必须在指令里 → 累加器必须归某个线程所有 → K 不可拆线程 → K 扩展只能吃寄存器 → K 扩展没有并行收益。
- 判断一条 mma 是否与另一条相关，只看两件事：**是否写同一组 D 寄存器**（写后读 = 依赖），以及**C 操作数是否是上一条的 D**（链式累加）。用这两把尺子去读任何 GEMM 的 SASS 都能读通。
- `RZ` 作 C 是个很典型的硬件设计：把"清零"这个高频操作塞进指令语义，省掉一条指令，也省掉一次寄存器写。

## 常见误区

1. **"mma 只做乘法，累加是额外代码"** → 错。`C` 是必需操作数，累加内建在指令里。
2. **"K 扩展和 M/N 扩展一样都能提高并行度"** → 错。只有 M/N 扩展产生独立链，K 扩展是串行链。
3. **"K 方向的 mma 可以分给不同线程加速"** → 错。会把归约代价引入，必须跨线程 shuffle/SMEM。
4. **"第一条 mma 的累加器初值无关紧要"** → 错。初值错误会污染整条累加链，这就是 `clear(tCrC)` 的意义。
5. **"SASS 里源操作数和目的操作数重名是抄错了"** → 不一定。硬件先读后写，重叠是合法的寄存器复用技巧。
