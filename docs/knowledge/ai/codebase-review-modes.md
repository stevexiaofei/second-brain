# 代码库审计 / 上手 / 深读 三分法

## 一句话理解

读一个新代码库时，我通常不是只做一种事，而是在三种目标之间切换：

- **代码库审计**：找问题、找风险、找 bug
- **代码库上手**：尽快跑起来、改起来、用起来
- **代码库深读**：建立长期稳定的系统认知

这三种目标的阅读方式不同，输出也应该不同。

## 为什么要分这三种模式

同样是读仓库：

- 审计时，我关心“哪里可能错”
- 上手时，我关心“最快怎么开始动手”
- 深读时，我关心“系统到底怎么组织起来”

如果不分模式，就容易混在一起：

- 审计变成了泛泛而谈的总结
- 上手变成了过度阅读
- 深读变成了零散笔记堆积

## 三种模式的区别

| 模式 | 核心目标 | 重点关注 | 输出形态 |
|---|---|---|---|
| **代码库审计** | 找出真实问题 | 正确性、边界、测试、风险、可复现性 | findings / 风险清单 / 修复建议 |
| **代码库上手** | 尽快开始使用和修改 | 入口、构建、运行、示例、目录、常见坑 | 快速上手卡片 / 运行指南 / first change 路径 |
| **代码库深读** | 建立长期认知 | 架构、状态、控制流、数据流、接口、热路径 | 系统图 / 术语表 / 阅读导览 / 原子笔记 |

## 代码库审计

### 适合什么时候用

- 需要找 bug
- 需要做 code review
- 需要做安全或稳定性检查
- 需要验证某个行为是否真的成立

### 常看什么

- 边界条件
- 错误处理
- 并发 / 状态同步
- 性能热点
- 测试覆盖
- 文档与实现是否一致

### 输出建议

- 问题按严重程度排序
- 每条都给证据
- 说明失败场景
- 说明为什么重要
- 说明下一步怎么验证

## 代码库上手

### 适合什么时候用

- 第一次接触仓库
- 想快速跑起来
- 想做第一个改动
- 想知道哪里是入口

### 常看什么

- README
- 构建 / 测试 / 运行命令
- 目录结构
- 配置文件
- 主入口文件
- 一个 happy path 示例

### 输出建议

- 这是什么仓库
- 怎么安装和运行
- 入口在哪里
- 第一处该改什么
- 常见坑有哪些

## 代码库深读

### 适合什么时候用

- 要长期维护某个仓库
- 要把仓库转化为自己的知识
- 要理解系统设计和实现细节
- 要写系列笔记或知识地图

### 常看什么

- 组件边界
- 数据流 / 控制流
- 状态和生命周期
- 缓存 / 队列 / 注册表
- 核心抽象
- 热路径
- fallback 路径
- tests 和 benchmark

### 输出建议

- 系统图
- 入口说明
- 核心抽象
- 关键状态表
- 阅读顺序
- 关联笔记
- 待回答的问题

## 默认选择规则

如果用户没有明确说要哪一种：

- 看到“审计 / review / bug / verify / 风险” → 选 **代码库审计**
- 看到“上手 / 入门 / 快速跑起来 / first change” → 选 **代码库上手**
- 看到“深读 / 精读 / 系统图 / 结构化理解 / 笔记整理” → 选 **代码库深读**

## 和通用阅读导览的关系

这篇是一个更上层的分流器。

真正执行时，通常会落到这些通用步骤：

- 先读仓库规则
- 再搜索已有文档和重复内容
- 再画架构图
- 再追踪关键数据流和控制流
- 再对比 docs / tests / code
- 再决定要不要沉淀成笔记
